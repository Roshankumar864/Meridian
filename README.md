# Meridian — marketing site

A five-page marketing site for a fictional B2B compliance-automation company.
Static HTML generated by [Eleventy](https://www.11ty.dev/). No framework, no
page builder, no client-side rendering, no third-party scripts.

- **Live URL:** _add after deploying — see [Deploying](#deploying)_
- **Performance and schema evidence:** [`docs/evidence/`](docs/evidence/README.md)
- 100 / 100 / 100 / 100 on Lighthouse mobile and desktop, every page

```bash
npm ci
npm run dev      # http://localhost:8080
npm run build    # -> _site/
npm run check    # structural audit of the built HTML
```

---

## Why this stack

The brief asks for a structure a content team can extend without touching layout
code, and for Core Web Vitals in the green on mobile. Those two goals point at
the same answer: put the content in data files, render it once at build time,
and ship a document that does almost nothing at runtime.

Eleventy gives that without a framework tax — the output is plain HTML, so the
performance ceiling is set by the markup rather than by a hydration step.

## Architecture

```
src/
  _data/            Content and configuration. This is where the content team works.
    site.js         Company details, contact, canonical URL, footer credit
    nav.json        Header and footer navigation
    features.json   Feature cards, grouped by page
    plans.json      Pricing tiers, comparison table, billing note
    faqs.json       FAQ sets, grouped by page
    proof.json      Logos, stats, testimonials, process steps, integrations
  _includes/
    layouts/
      base.njk      <head>, meta, JSON-LD, landmarks, skip link, footer
      page.njk      Renders the page's `sections` array in order
    components/
      section.njk   Maps a section `type` to markup — the one dispatch point
      header.njk    Primary nav
      footer.njk    Footer nav, legal, required credit line
      contact-form.njk
      breadcrumbs.njk
      icons.njk     Inline SVG macro
  assets/css/main.css   Design tokens + components; inlined into <head> at build
  assets/img/           Logo, favicon, generated OG card and touch icons
  *.njk                 One file per page: front matter only, no markup
tools/
  audit.js          Structural checks over built HTML (npm run check)
  lighthouse.js     Lighthouse sweep, mobile + desktop (npm run lh)
  summarise.js      Rebuilds docs/evidence/summary.md
  build-images.js   Generates og.png and the raster icons from SVG
```

### The composition model

A page is an ordered list of sections declared in its own front matter. There is
no page-specific markup anywhere:

```yaml
---
layout: layouts/page.njk
permalink: /pricing/
title: "Pricing"
description: "..."
faqSource: pricing        # also drives the FAQPage schema
sections:
  - type: hero
    heading: Priced on scope, not on pressure
    intro: >-
      Three plans, published numbers...
  - type: pricing
    tone: soft
    heading: Choose a plan
  - type: faq
    heading: Pricing questions
    source: pricing       # -> faqs.json
---
```

Every section block honours the same contract: `id`, `tone` (`soft` | `dark`),
`eyebrow`, `heading`, `intro`, and `source` (a key into the matching data file).

**Available section types:** `hero`, `features`, `steps`, `stats`, `logos`,
`integrations`, `quotes`, `pricing`, `comparison`, `faq`, `prose`, `contact`,
`cta`.

### What a content team can do without a developer

| Task | Where |
| --- | --- |
| Reword any heading, intro or CTA | The page's front matter |
| Reorder, add or remove a section on a page | Move a list item in `sections` |
| Change a background treatment | `tone: soft` / `tone: dark` on the section |
| Edit feature cards, FAQs, testimonials, stats, logos | `src/_data/*.json` |
| Change a price, a plan's contents or the comparison table | `src/_data/plans.json` |
| Add a whole new page | Copy a `.njk` file, change `permalink` and `sections` |
| Change nav or footer links | `src/_data/nav.json` |
| Change company details, address, social links | `src/_data/site.js` |

All of those propagate to the meta tags, the sitemap and the structured data
automatically. A price change in `plans.json` updates the pricing cards, the
comparison table and the schema `Offer` in one edit.

Only adding a *new kind* of section requires touching `components/section.njk`.

## Accessibility

Built to WCAG 2.2 AA. Lighthouse accessibility is 100 on every page, but that
audit only covers what a machine can see — the rest was done by hand.

- **Semantics.** One `<h1>` per page, no skipped heading levels (enforced by
  `npm run check`), real `<header>` / `<nav>` / `<main>` / `<footer>` landmarks,
  `<article>` for cards, `<figure>`/`<blockquote>` for testimonials, `<dl>` for
  contact details, a `<table>` with `<caption>`, `scope="col"` and `scope="row"`
  for the plan comparison.
- **Keyboard.** Skip link to `<main tabindex="-1">`; a single visible focus ring
  (3 px, recoloured on dark sections) via `:focus-visible`; the mobile nav is a
  real `<button>` with `aria-expanded` and `aria-controls`; FAQs are
  `<details>`/`<summary>`, which are keyboard-operable with no JavaScript; the
  comparison table is a focusable scroll region so it can be panned by keyboard;
  no positive `tabindex`, no focus traps, DOM order matches visual order.
- **Forms.** Every control has a visible `<label>`, related fields are grouped in
  a `<fieldset>` with a `<legend>`, hints are wired with `aria-describedby`,
  required fields are marked in text (the asterisk is `aria-hidden` with a
  screen-reader equivalent), touch targets are ≥ 44 px, and `autocomplete`
  attributes are set. Validation is native HTML — no JS to fail.
- **Content.** `aria-current="page"` on the active nav item and the last
  breadcrumb; decorative SVGs are `aria-hidden`; `—` in the comparison table
  carries a "Not included" text equivalent; link text stands alone out of
  context.
- **Preferences.** `prefers-reduced-motion` disables smooth scrolling and
  transitions. Layout is fluid to 320 px and reflows to a single column with no
  horizontal scroll; text scales with `clamp()` and survives 200% zoom.
- **No-JS.** Nothing is JS-dependent. The mobile nav only collapses once a `js`
  class is set on `<html>`, so with scripting disabled the full nav stays in the
  flow rather than becoming unreachable.

## SEO and structured data

Each page carries a canonical URL, a unique title and description, full Open
Graph and Twitter card tags, a 1200×630 OG image, and a JSON-LD `@graph`.

The graph is assembled in `eleventy.config.js` from the same data that renders
the page — see [`docs/evidence/README.md`](docs/evidence/README.md) for the
node-by-node breakdown. `sitemap.xml`, `robots.txt` and `site.webmanifest` are
generated; `/thanks/` and `/404.html` are `noindex`.

## Performance

Full detail and the reproduction steps are in
[`docs/evidence/README.md`](docs/evidence/README.md). Summary: CSS is inlined,
there are no webfonts, no raster images in the layout, ~400 bytes of inline JS,
and no third-party requests. LCP 1.1 s on throttled mobile, CLS 0, TBT 0 ms.

## Deploying

The build output is a plain static directory, so any static host works.

**Netlify** (recommended — `netlify.toml` is committed with cache headers, CSP
and the other security headers, and the contact form is wired to Netlify Forms):

1. Push this repo to GitHub.
2. Netlify → *Add new site* → *Import an existing project*, pick the repo.
3. Build command `npm run build`, publish directory `_site` (both pre-filled
   from `netlify.toml`).
4. Set `SITE_URL` to the final domain so canonical URLs and JSON-LD resolve
   correctly. Netlify's own `URL` variable is picked up automatically.

**Anything else** (Cloudflare Pages, Vercel, S3): build command `npm run build`,
output `_site`, Node 20+. Set `SITE_URL`.

### The contact form

A static site has no server, so the POST needs a service to receive it. The
target is configured in the `form` block of `src/_data/site.js` — `action`,
whether to emit the Netlify attributes, and any hidden fields the provider
requires. Switching providers is a config edit, not a template change.

If you use **Netlify Forms**, two things are required and both are easy to miss:

1. **Project configuration → Forms → enable Form detection.** New Netlify sites
   have this off by default.
2. **Redeploy afterwards.** Detection runs at build time, so an existing deploy
   will not pick it up — trigger *Clear cache and deploy site*.

Symptom when either step is missed: `POST` returns 404 on every path (including
`/`) while `GET /thanks/` returns 200 — the submission falls through to the
static file server, which has no route for a POST.

3. **Forms → Notifications → Email notification.** Netlify stores submissions in
   the dashboard and does *not* email them by default.

Providers that need no host support (and therefore no toggle) are documented
alongside the config in `site.js`.

GitHub Pages works too, but a *project* Pages site is served from
`/<repo>/`, which breaks the root-relative URLs. Use a custom domain or a
`username.github.io` repo if you go that route.

`.github/workflows/ci.yml` runs the build, the structural audit and the full
Lighthouse sweep on every push, and uploads the reports as artefacts.
